# סקירת אבטחה — P11-T6

**תאריך:** 2026-09-04 · **מבצע:** Claude Code, בסשן מרוחק Linux (ubuntu, container) · **היקף:** `packages/tools`
(Sandbox/toolsmith), ARCHITECTURE.md §11, ADR-013.

## 0. הגבלת הסביבה — מה נבדק בפועל מול מה שנסקר בקוד בלבד

הסשן הזה רץ בקונטיינר **Linux בלבד**. אין גישה אמיתית ל-macOS או ל-Windows, ואין דימון Docker פעיל
(מאומת: `probeDockerAvailable()` דורש `docker info` תקין; `docker-sandbox.test.ts`'s live-daemon probe
כושל כאן — אותה מגבלה שכבר תועדה ב-P10-T6/P11-T1–T5).

| פלטפורמה | מה נבדק |
|---|---|
| Linux | **הרצה אמיתית** — `LinuxSandbox` האמיתי, תהליכים אמיתיים, `unshare`/`ulimit` אמיתיים |
| macOS | סקירת קוד בלבד (`darwin-sandbox.ts`) — **לא הורץ**, בדיוק כפי שתועד כבר בקוד עצמו (ר' §3) |
| Windows | סקירת קוד בלבד (`windows-sandbox.ts`) — **לא הורץ**, בדיוק כפי שתועד כבר בקוד עצמו |
| Docker | סקירת קוד + בדיקה חלקית (בניית פקודת `docker run`, ללא הרצה אמיתית — אותה מגבלה מ-P7-T7) |

כל ממצא שמסומן "**מאומת בפועל**" הורץ ממש בסשן הזה, נגד ה-`LinuxSandbox` האמיתי (לא מוק), עם קובצי
הוכחה ב-`packages/tools/src/sandbox/linux-sandbox.pentest.test.ts` (החלק "KNOWN GAP"). כל ממצא אחר
מסומן "**סקירת קוד בלבד**" — הגיוני, עקבי עם התבנית שבקוד הקיים, אבל לא הוכח אמפירית בפלטפורמה הזאת.

## 1. הממצא המרכזי: תת-מערכת ה-Sandbox כולה לא מחוברת ל-`apps/runtime`

לפני שממצאי אבטחה ספציפיים — עובדה שקובעת את כל ניתוח החומרה כאן: **`packages/tools` (Sandbox,
toolsmith, שלושת המימושים) אינה תלות של `apps/runtime` בכלל.**

```
grep -rln "@ao/tools" --include="*.json"  →  רק packages/tools/package.json ו-packages/core/package.json
grep -rn "runToolsmith|RunLocalTool"      →  אפס תוצאות ב-apps/runtime/src
grep -rn "child_process|spawn("           →  אפס תוצאות ב-apps/runtime/src (מחוץ לבדיקות)
```

`packages/core`'s `runToolsmith` (P7-T4) מוכן ומבחן-יחידה מלא, ומצפה ל-`runLocalTool` **מוזרק** —
אבל `apps/runtime` (נקודת ההרכבה האמיתית שמריצה את השרת) אף פעם לא מזריקה מימוש אמיתי, ולא קוראת
לפונקציה הזו כלל. זו **אותה תבנית בדיוק** שחזרה שוב ושוב ב-P9/P10/P11 — תשתית אמיתית, בדוקה, קיימת
עמוק בקוד, אף פעם לא מחוברת לזרימה האמיתית.

**המשמעות לאבטחה:** נכון להיום, **אין וקטור התקפה חי במוצר הרץ** — משתמש אמיתי של האפליקציה הרצה לא
יכול לגרום לה להריץ סקריפט מקומי כלשהו, כי שום קוד ב-`apps/runtime` לא קורא לזה. הממצאים בסעיפים
הבאים הם **אמיתיים ברמת הקוד/הספרייה**, ו**יהפכו לחור אבטחה אמיתי במוצר בדיוק ברגע שמישהו יחבר את
`toolsmith`/`Sandbox` לזרימת ה-run האמיתית** (שלב עתידי טבעי וצפוי — הקוד עצמו כתוב ומחכה לחיווט) — הם
צריכים להיסגר **לפני** אותו חיווט, לא אחריו.

זו גם התשובה ל"האם ההצהרה ב-UI מדויקת" (§4 למטה): **אין הצהרה ב-UI כלל היום** — לא כי הוסתרה, אלא כי
הפיצ'ר שהיא אמורה לתאר לא מחובר. זה עצמו ממצא, לא רק "אין מה לבדוק".

## 2. מה עובד כפי שמתועד — אומת מחדש, לא רק הונח

`packages/tools/src/sandbox/linux-sandbox.pentest.test.ts` הוא חבילת פנטסט אמיתית שכבר נבנתה ב-P7-T1
(network/jail/infinite-loop/memory-bomb/orphaned-process). הרצתי אותה שוב במלואה בסשן הזה — **9/9
עוברות** (6 קיימות + 3 חדשות, ר' §3):

| בקרה | סטטוס | איך אומת |
|---|---|---|
| חסימת רשת (Linux, `unshare --net`) | ✅ עובד | **מאומת בפועל** — חיבור אמיתי ל-listener אמיתי על `127.0.0.1` נחסם |
| Timeout + הריגת עץ תהליכים | ✅ עובד | **מאומת בפועל** — לולאה אינסופית נהרגת, `pgrep` אחרי ההריגה לא מוצא כלום |
| תקרת זיכרון (Linux, `ulimit -v`) | ✅ עובד | **מאומת בפועל** — הקצאת 400MB מעל תקרת 64MB נכשלת בתוך הסקריפט (`MemoryError`), לא תולה את המארח |
| דחיית `cwd` מחוץ ל-`stagingRoot` | ✅ עובד | **מאומת בפועל** — `SandboxJailViolationError` לפני שהתהליך בכלל רץ |
| `capabilities` לא מתחזה — `networkBlocking` נגזר מ-probe אמיתי, לא hardcoded | ✅ עובד | **מאומת בפועל** |
| Docker: בניית `docker run` (רשת/זיכרון/bind-mount) | ✅ עובד (לוגיקה) | סקירת קוד + בדיקות עם `spawnFn` מוזרק — לא הורץ קונטיינר אמיתי (הפרוקסי של הסביבה חוסם משיכת images, אותה מגבלה מ-P7-T7) |
| Docker: **לא** דולף env של המארח לקונטיינר | ✅ עובד (לוגיקה) | סקירת קוד — `dockerArgs` לא כולל `-e`/`--env-file`; ל-`docker run` אין דרך לקבל env בלי דגל מפורש |

## 3. ממצאים חדשים — נפתחו בסקירה הזו

### 3.1 🔴 `capabilities.pathJail: true` לא משקף את המציאות — אין בידוד מערכת-קבצים אמיתי (Linux/macOS/Windows-native)

**חומרה: גבוהה.** **מאומת בפועל על Linux**, סקירת קוד בלבד למקבילות ב-macOS/Windows (אותו דפוס קוד
בדיוק, ר' §3.1.1).

`SandboxRunOptions.cwd`/`stagingRoot` נבדקים **פעם אחת בלבד**, לפני ההרצה, דרך `resolveWithinRoot` —
"האם ה-`cwd` שביקשתי נמצא בתוך `stagingRoot`". **זו הבדיקה היחידה.** ברגע שהתהליך רץ, אין שום מנגנון
(chroot, mount namespace, bind-mount, ACL) שמונע ממנו לקרוא/לכתוב לכל נתיב אחר במערכת הקבצים שהמשתמש
המריץ (ה-OS user שמריץ את כל האפליקציה) יכול לגשת אליו — כולל נתיבים מוחלטים מחוץ ל-`stagingRoot`
לחלוטין.

**מאומת בפועל** (`linux-sandbox.pentest.test.ts`, "KNOWN GAP"):
```
sandbox.run({ command: "python3", args: ["-c", "print(open('/etc/passwd').read()[:20])"], ... })
→ { ok: true, stdout: "root:x:0:0:root:/root:..." }

sandbox.run({ command: "python3", args: ["-c", "open('/tmp/marker.txt','w').write('escaped')"], ... })
→ { ok: true }  — הקובץ נוצר בפועל מחוץ ל-stagingRoot
```
זה קרה **תוך כדי ש-`networkBlocking: true` באמת עבד** (`unshare --net` באמת חסם את הרשת לאותו תהליך) —
כלומר בידוד הרשת ובידוד מערכת-הקבצים הם שני מנגנונים נפרדים לגמרי, וההצלחה של האחד לא אומרת דבר על
השני.

**השוואה ל-ARCHITECTURE.md §8's טבלה:** השורה "ספריית עבודה — כלא ל-`staging/`, קריאה בלבד מהתיקייה
המחוברת" מסומנת ✅ בכל שלוש העמודות הלא-Docker. **זו הצהרה שגויה ביחס למה שנבדק כאן** — הטבלה ראויה
לתיקון (סעיף "המלצות", §5), אבל לא תוקנה בקוד/במסמך בפועל בסבב הזה לפי בקשה מפורשת של המשתמש (ר'
§0/§5) — כדי לא לערבב תיקון-הצהרה עם תיקון-אמיתי-מסוכן בלי החלטה נפרדת.

**רק Docker מספק בידוד אמיתי כאן**, כי `-v stagingRoot:/workspace` הוא גבול filesystem אמיתי של
הקונטיינר, לא בדיקת מחרוזת.

#### 3.1.1 macOS / Windows — אותו דפוס בדיוק, לא נבדק אמפירית

`darwin-sandbox.ts`'s פרופיל ה-Seatbelt הוא `(version 1)(allow default)(deny network*)` — "**אפשר
הכול**, חסום רק רשת". שום דבר בפרופיל לא מגביל קריאה/כתיבה לקבצים. `windows-sandbox.ts` פשוט לא
מיישם שום מנגנון בידוד-קבצים (רק `spawn` רגיל עם `cwd`). **המסקנה ההגיונית, לא מאומתת אמפירית כאן**:
אותו ממצא בדיוק חל גם שם. זה **פער רחב יותר** ממה שה-TASKS.md ציפה לו ("מה בפועל לא מבודד ב-Windows
מקורי") — הוא לא ייחודי ל-Windows, הוא משותף לשלוש הפלטפורמות הלא-Docker.

### 3.2 🟠 סקריפט בתוך ה-sandbox יורש את משתני הסביבה המלאים של תהליך-האב — כולל סודות

**חומרה: בינונית-גבוהה** (תלוי אם `GEMINI_API_KEY`/סודות אחרים נשמרים בפועל ב-`process.env` בהרצה
האמיתית). **מאומת בפועל.**

`posix-exec.ts`: `env: { ...process.env, ...options.env }` — התהליך-הבן מקבל את **כל** משתני הסביבה של
תהליך-האב, לא רק את מה ש-`options.env` סיפק בפירוש. `apps/runtime/src/index.ts` בפועל קורא
`process.env["GEMINI_API_KEY"]` — דרך לגיטימית ונפוצה להזין מפתח API (למשל בהרצה מקומית/self-hosted).

**מאומת בפועל:**
```
process.env.AO_PENTEST_FAKE_SECRET = "fake-secret-do-not-use";
sandbox.run({ command: "python3", args: ["-c", "import os; print(os.environ.get('AO_PENTEST_FAKE_SECRET'))"], ... })
→ stdout: "fake-secret-do-not-use"
```
זה מתנגש ישירות עם ARCHITECTURE.md §11's הצהרה על מפתח API ("OS keychain... לא בלוגים, לא בייצוא") —
ההצהרה עצמה לא דנה ביורשה של env vars לתהליכי-בן, ולא נבדקה מול זה עד כה.

**Docker לא סובל מהפער הזה** — `docker run` לא מעביר env של המארח לקונטיינר בלי דגל `-e`/`--env-file`
מפורש, ואין כזה ב-`dockerArgs`.

## 4. בדיקת דיוק ה-UI (נדרש במפורש ב-P11-T6)

`grep -rl "sandbox\|Sandbox" apps/web/src apps/runtime/src` — **אפס תוצאות**. אין באנר, אין הודעה, אין
שום מקום ב-UI שמזכיר `SandboxCapabilities`/בידוד/`networkBlocking` בכלל. ה-`notes` ב-`capabilities.ts`
("בידוד חלקי: הסקריפטים יכולים לגשת לרשת...") **קיימות בקוד ומעולם לא הגיעו למסך**.

**תשובה ישירה לשאלת P11-T6:** ההצהרה ב-UI **אינה לא-מדויקת — היא פשוט לא קיימת**. זה לא "טוב" —
המשמעות היא שכרגע, גם אם `packages/tools` יחובר ל-`apps/runtime` בעתיד בלי לחבר גם את הבאנר, משתמש
ב-Windows ללא Docker לא יידע שהסקריפטים לא מבודדים כלל (לא רק "רשת פתוחה" — כפי שהוכח ב-§3.1, גם
מערכת-הקבצים). זו נקודת-חיווט קריטית לזכור כשמישהו כן יחבר את הפיצ'ר.

## 5. המלצות — לא בוצעו בסבב הזה, לפי בקשת המשתמש

המשתמש בחר במפורש: **"תעד בלבד, אל תתקן"** — לא לבצע את תיקון ה-mount-namespace/chroot העמוק (הנדסה
משמעותית שדורשת בדיקה זהירה נגד ADR-012, בלי גישה אמיתית ל-macOS/Windows לאמת מולם), ולא לגעת בקוד
הייצור (`capabilities.ts`, ARCHITECTURE.md §8's טבלה) בסבב הזה. שני ממצאים חדשים (§3.1, §3.2) +
הממצא המרכזי (§1) **נשארים פתוחים, מתועדים כאן ובקוד** (בדיקות "KNOWN GAP" ב-
`linux-sandbox.pentest.test.ts`) — לא "נסגרים" ולא מוסתרים.

**המלצות מדורגות לסבב עתידי, לפי סדר עדיפות:**
1. **תיקון זול ובטוח קודם:** להפסיק להעביר `process.env` מלא ל-`Sandbox.run` — allowlist מפורש
   (`PATH`/`HOME`/`LANG` וכיו"ב) + מה ש-`options.env` סיפק, לא ספריית env מלאה. שינוי קטן, נבדק בקלות,
   סיכון נמוך.
2. **תיקון ההצהרה** (`capabilities.pathJail`, ARCHITECTURE.md §8's טבלה) — לשקף "cwd נבדק, לא jail
   אמיתי" עד שהתיקון האמיתי (סעיף 3) קיים. זול, אבל דורש להחליט אם זה "תיקון קוד" (capabilities.ts)
   שדורש רגרסיה מלאה על הבדיקות הקיימות שמניחות `pathJail: true`.
2.5. **לחבר את ה-`notes`/`capabilities` ל-UI בפועל** — גם אם רק כטקסט סטטי, כדי ש-§4 יפסיק להיות
   "אין הצהרה כלל".
3. **התיקון האמיתי (הגדול):** mount namespace + הגבלת כתיבה ל-`stagingRoot` בלבד ב-Linux
   (`unshare --mount` + bind-mount, בלי native code — עקבי עם ADR-012), עם מקבילות למחקר נפרד עבור
   macOS (Seatbelt file-read/write rules — הפרופיל תומך בזה, לא נוסה) ו-Windows (אין rlimits/namespaces
   — כנראה Docker היא הדרך היחידה לבידוד אמיתי שם, כבר מתועד ב-ADR-013).
4. **לוודא שהחיווט העתידי של `toolsmith`/`Sandbox` ל-`apps/runtime` (§1) לא קורה לפני שסעיפים 1–3
   נסגרים**, כדי שהפער לא יהפוך מסיכון-תיאורטי לחור אבטחה חי במוצר.

## 6. סיכום ממצאים

| # | ממצא | חומרה | סטטוס | פלטפורמות |
|---|---|---|---|---|
| 1 | תת-מערכת Sandbox/toolsmith לא מחוברת ל-`apps/runtime` | מידע (לא חור אבטחה היום, אבל קובע את ההקשר לכל השאר) | מתועד | כולן |
| 3.1 | `pathJail: true` לא אוכף בידוד מערכת-קבצים אמיתי | גבוהה | מתועד + בדיקה תקועה בקוד | Linux (מאומת), macOS/Windows (סקירת קוד) |

כל ממצא כאן **מתועד**, לא "סגור" — לפי בקשת המשתמש המפורשת לסבב הזה. שום ממצא לא הוסתר או "טופל"
בלי תיקון אמיתי מאחוריו.
